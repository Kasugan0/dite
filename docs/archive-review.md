# 历史设计审计

本文档用于审视 `docs/archive/` 下的历史设计文件，并把它们和当前实现对齐。

它不是 archive 的重写版，而是一层过滤器。

## 为什么需要这份文档

archive 里有不少有价值的思考，但它同时也混入了这些东西：

- 已经过时的假设
- 从未实现过的计划
- 只实现了一部分、而且落地形态已经不同的想法
- 已经被当前代码证明没必要继续走的路线

如果没有这一层审计，archive 很容易被误读成“当前现状”或“未来优先级清单”。

## 审计方法

这里把 archive 里的内容分成四类：

1. 已经被当前代码吸收
2. 只实现了一部分，或者落地形态变了
3. 仍然值得保留为未来候选
4. 当前应当暂停或不作为主线方向

## 1. 已经被当前代码吸收的部分

这些内容已经在当前实现中得到验证，不再属于未来规划。

### 文本优先提取

来源：

- `docs/archive/DESIGN.md`
- `docs/archive/PHASE2_DESIGN.md`

当前现实：

- embedding 输入直接来自提取后的文本内容
- VLM 被当成回退路径，尤其用于弱 PDF 提取

为什么重要：

- 这已经不是一个未来想法，而是当前系统的核心原则之一

### HDBSCAN 加 k-NN 修复

来源：

- `docs/archive/DESIGN.md`
- `docs/archive/PHASE2_DESIGN.md`

当前现实：

- HDBSCAN 仍然是核心聚类步骤
- k-NN 修复已经作为可选后处理存在

### 分层 SQLite 缓存

来源：

- `docs/archive/DESIGN.md`
- `docs/archive/PHASE1_DESIGN.md`
- `docs/archive/PHASE3_DESIGN.md`

当前现实：

- 主提取内容、VLM 回退内容、embedding 已经分层保存
- VLM 和 embedding 都有版本控制
- 重复文件按哈希复用已经真实存在

### 安全预览与脚本导出

来源：

- `docs/archive/PHASE1_DESIGN.md`

当前现实：

- 预览模式已经存在
- 脚本导出已经存在
- 直接执行仍然采用复制、校验、再删除的保守路径

## 2. 只部分实现或落地形态已变化的部分

这些东西不能说“没做”，但也不能按 archive 原文理解。

### 同名簇合并

archive 当年的说法：

- 同名簇合并被当成默认内建行为

当前现实：

- 核心合并函数存在
- 它发生在簇命名之后
- 当前 CLI 流程明确关闭它
- 它只能合并“已经被拆开、而且最后又碰巧拿到了同一个名字”的簇

结论：

- 它不是聚簇根因的修复
- archive 当年把它写得太像主解法了，但按今天的代码看，它更像症状级后处理

### 语义分析器

archive 当年的说法：

- 语义分析层曾被提出、被推迟，后来又被当成可选增强

当前现实：

- `src/dite/core/analyzer.py` 存在
- 它有测试
- 主流水线并不把它作为生产路径

结论：

- 它更像一个实验性分支，不是当前产品方向

### 异步 / 并发处理

archive 当年的说法：

- 异步处理被写成未来功能或独立里程碑

当前现实：

- 提取层已经有受限并发
- 簇命名和 VLM 请求已经有受限并发
- `AsyncRequestRuntime` 已经存在

结论：

- 它不是完全未触达的未来功能
- 后续应当被当成运行时调优与扩展，而不是全新的主题

### 缓存修复与大小限制

archive 当年的说法：

- VLM 缓存 upsert 和缓存大小限制曾被写成未来修复项

当前现实：

- VLM 内容更新已经是 upsert 语义
- 缓存大小限制已经实现

结论：

- 这些属于已经关闭的规划项，不该继续挂在路线图上

## 3. 仍然值得保留的未来候选

这些是 archive 里今天仍然值得认真看待的候选方向。

### 可撤销的整理执行

为什么保留下来：

- 它直接解决当前最危险的用户动作
- 它和现有保守执行流天然配套

### HTML 报告导出

为什么保留下来：

- 它可以扩展当前报告输出，而不需要改变运行模型

### 更好的缓存可观测性

为什么保留下来：

- 缓存复用是实际性能的核心能力
- 当前可见性仍然偏粗

### Watch 模式

为什么保留下来：

- 它可能服务真实的热文件夹工作流

为什么仍然只是中期项：

- 它会扩大后台行为和运行风险

### 长文档分块

为什么保留下来：

- 它可能帮助解决真实的长文档或多主题误聚类问题

为什么仍然是条件项：

- 它会同时抬高多个层面的复杂度

### 多提供商支持

为什么保留下来：

- 当前 OpenAI-compatible 形态未必永远够用

为什么仍然只是中期项：

- 提供商抽象会影响几乎所有 API 相关表面

### 模板化整理

为什么保留下来：

- 当“发现结构”不够时，某些领域可能需要“套用结构”

为什么仍然只是中期项：

- 它会把产品范围推向字段提取与结构化输出

## 4. 当前应暂停或不作为主线方向的部分

这些内容今天不应当驱动主线规划。

### 语义分析器作为默认主路径

为什么暂停：

- 当前代码已经证明更简单的直接 embedding 路径更划算
- archive 自己后期也已经承认这条路代价更高

### 图片重命名

为什么暂停：

- 它会引入另一类不可逆文件操作
- 它离当前产品核心价值较远

### Prompt 管理子系统

为什么暂停：

- 当前 prompt 面积太小，不值得单独做成子系统

### “增量扫描”作为一级能力

为什么暂停：

- archive 很容易把缓存复用和真正的增量聚类混在一起
- 当前系统的大部分收益其实已经通过缓存和重复文件折叠拿到了

### 基于 Hidden States 的研究路线

为什么暂停：

- 研究上有意思
- 但离当前部署模型和产品范围太远

## 哪些 archive 文件今天仍然最有参考价值

如果确实要回看 archive，下面这些文件的信号密度仍然最高：

- `docs/archive/DESIGN.md`
  - 适合看第一代设计原则
- `docs/archive/PHASE1_DESIGN.md`
  - 适合看 CLI、缓存和安全执行的早期思路
- `docs/archive/PHASE2_DESIGN.md`
  - 适合看聚类与 PDF 回退的动机
- `docs/archive/PHASE4_DESIGN.md`
  - 适合看撤销和报告类想法的雏形

这些文件现在直接拿来做规划时可信度较低：

- `docs/archive/PHASE3_DESIGN.md`
  - 混入了真实想法、已经实现的修复项和过度承诺的路线语言
- `docs/archive/FUTURE.md`
  - 更适合做研究灵感来源，不适合直接当产品计划
- `docs/archive/pdf-processing-technical-report.md`
  - 更像外部架构参考，而不是本仓库实现说明

## 和当前规划文档的关系

现在更合理的阅读顺序应该是：

1. 先读 `docs/overview.md`，确认今天什么是真的
2. 再读 `docs/roadmap.md`，确认什么还值得规划
3. 再读 `docs/archive-review.md`，理解 archive 应该怎么用
4. 最后只有在需要历史上下文时，才回头读 `docs/archive/`
