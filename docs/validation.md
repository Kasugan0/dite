# 验证集规范

本文档定义 DITE 当前用于聚类验证的样本分层、目录约定、标注格式、评估流程和默认参数晋升门槛。

它的目标不是学术完美，而是防止我们继续凭感觉调聚类。

如果本文档与代码冲突，以代码为准；如果本文档与一次性实验结论冲突，以人工复核后的真实失败案例为准。

## 核心原则

- `docs/test/valid` 保留，但只作为回归集，不作为唯一裁判。
- 默认参数只能由代表性验证集决定，不能只由仓库内样本决定。
- A/B 结果必须能回答“哪些文件变了”，不能只看总簇数。
- 评估必须同时看拆簇、误并和噪音，不允许只追求某一个指标好看。
- 新验证样本进入主集之前，必须先说明它在补哪种失败模式。

## 验证集分层

验证集固定分成三层。

### 1. 回归集

用途：

- 防止代码重构后把已知行为改坏。
- 提供 CI 和快速 smoke 的稳定样本。

来源：

- 当前仓库内的 `docs/test/valid`
- 少量已确认的失败案例切片

要求：

- 样本规模控制在 `20-60` 个文件
- 可以提交到仓库
- 文件结构长期稳定，不频繁增删

必须覆盖：

- 重复文件和重命名副本
- 同主题不同格式
- 短文本
- PDF 提取弱样本
- 容易拆成多个小簇的样本

限制：

- 回归集不能单独决定默认参数
- 回归集只负责“防退步”，不负责“证明最优”

### 2. 代表性验证集

用途：

- 作为 A/B 和参数实验的主裁判
- 决定默认聚类参数是否应该晋升

来源：

- 真实目录样本
- 接近真实使用场景的混合目录

要求：

- 至少 `3` 个目录，建议 `3-5` 个
- 每个目录建议 `50-200` 个文件
- 目录之间的内容类型和混乱程度要明显不同

最低覆盖的目录类型：

- 学习资料目录
- 工作文档目录
- 下载目录或收件箱式杂乱目录

建议额外覆盖：

- 图片和扫描 PDF 较多的目录
- 多种 Office 文件混合的目录
- 含大量重复副本和版本副本的目录

规则：

- 代表性验证集不要求全部进仓库
- 但必须有稳定的目录清单、来源说明和人工标签

### 3. 对抗集

用途：

- 故意攻击当前已知弱点
- 否决看起来平均更好、实际上边界更烂的方案

来源：

- 手工挑选或手工构造
- 来自真实失败案例的最小切片

要求：

- 建议 `10-30` 个文件
- 文件数可以小，但失败模式必须明确

必须优先覆盖：

- 文件名很像但内容不同
- 内容相近但文件名完全不同
- 极短文本
- OCR 噪声 PDF
- 同主题小簇
- 多语言混杂
- 课件、讲义、论文、截图混在一起的目录

规则：

- 对抗集不负责挑选最佳参数
- 对抗集负责否决明显糟糕的参数组合

## 目录与命名约定

验证集目录固定使用下面的逻辑分层：

```text
validation/
  regression/
  rep/
  adv/
```

如果样本需要进仓库，放在仓库内的 `docs/validation/` 或未来单独的数据目录。

如果样本不进仓库，也必须在本地或团队共享位置保持相同结构。

每个目录都要有一个 `manifest.json`。

建议命名：

- `regression/<set_name>/`
- `rep/<set_name>/`
- `adv/<set_name>/`

其中 `<set_name>` 应该表达失败模式或来源，而不是日期。

好例子：

- `rep/mixed-study-and-finance`
- `adv/filename-collision-short-text`
- `regression/pdf-weak-text-baseline`

坏例子：

- `set1`
- `new_test`
- `2026-05-23`

## 标注格式

每个验证集目录必须带一个 `manifest.json`，最小结构如下：

```json
{
  "name": "mixed-study-and-finance",
  "tier": "representative",
  "description": "Mixed real-world folder with study notes, finance docs, and duplicates.",
  "owner": "team",
  "files": [
    {
      "path": "ml_regression.txt",
      "cluster_id": "ml_notes",
      "must_link": ["ml_deep_learning.md"],
      "must_not_link": ["finance_statement.txt"],
      "notes": "Same topic as other ML notes."
    }
  ]
}
```

字段要求：

- `name`
  - 必填
  - 集合唯一标识
- `tier`
  - 必填
  - 只能是 `regression`、`representative`、`adversarial`
- `description`
  - 必填
  - 一句话说明这套样本为什么存在
- `owner`
  - 必填
  - 负责维护这套样本的人或团队
- `files`
  - 必填
  - 每个文件一条记录

每个文件记录要求：

- `path`
  - 相对路径
  - 必须和目录中的真实文件一致
- `cluster_id`
  - 必填
  - 人工认为“应该在一起”的组
- `must_link`
  - 可选
  - 必须聚到一起的文件列表
- `must_not_link`
  - 可选
  - 绝对不应该聚到一起的文件列表
- `notes`
  - 可选
  - 用于说明这个文件为什么重要

## 标注规则

标注时只做三件事，不搞花哨体系。

### 1. 先标 `cluster_id`

规则：

- 同一个 `cluster_id` 表示人工认为应归为同一类
- 不同 `cluster_id` 表示默认不应混到一起

命名要求：

- 使用稳定、可读的英文 snake_case
- 不要用数字流水号

好例子：

- `ml_notes`
- `finance_reports`
- `linear_algebra_books`

坏例子：

- `1`
- `cluster_a`
- `misc2`

### 2. 再补强制关系

只在需要时写：

- `must_link`
- `must_not_link`

使用场景：

- 边界特别重要的文件
- 容易被文件名误导的文件
- 容易被粗暴合并的文件

### 3. 允许噪音组，但不能滥用

当文件确实不属于任何稳定主题簇时，可以标成：

- `noise_misc`

但限制：

- 不能把“不想仔细标”的文件都丢进 `noise_misc`
- 代表性验证集中，`noise_misc` 占比建议不超过 `15%`

## 样本组成要求

每个代表性验证集都必须尽量覆盖下面这些维度。

### 文件类型

至少包含：

- PDF
- Markdown 或 TXT
- 至少一种 Office 文档

建议包含：

- 图片

### 内容长度

至少包含：

- 极短文本
- 正常文本
- 超长文本

### 内容质量

至少包含：

- 干净文本
- OCR 噪声文本
- 提取质量边缘样本

### 文件名质量

至少包含：

- 命名规范文件
- 命名很差的文件
- 只有编号或日期的文件

### 主题关系

至少包含：

- 明显同类
- 边界模糊
- 容易被误拆
- 容易被误并

### 重复关系

至少包含：

- 完全重复
- 改名重复
- 同主题不同版本

## 评估流程

每次实验按固定顺序走，不跳步。

### 阶段 1：E2E smoke

目的：

- 确认正式路径没坏

必须跑：

- `dite scan`
- `dite organize --dry-run`

按需跑：

- `dite pdf-check`

通过条件：

- 命令成功执行
- 输出 JSON 结构完整
- 没有明显的用户可见异常

### 阶段 2：输入模式 A/B

目的：

- 判断文件名混入是否在拉偏结果

工具：

- `tools/cluster_experiments.py compare-inputs`

必须看：

- `diff.entries`
- `initial_num_clusters_delta`
- `final_num_clusters_delta`
- `num_noise_delta`

通过条件：

- 能解释“哪些文件变了”
- 文件级变化和人工直觉大体一致

### 阶段 3：基础参数 sweep

目的：

- 在不引入更重流程的前提下比较默认参数候选

工具：

- `tools/cluster_experiments.py sweep`

基础 sweep 默认只看：

- `input_mode`
- `min_cluster_size`
- `min_samples`
- `cluster_selection_epsilon`
- 保持 `cluster_selection_method="eom"`

必须看：

- `fragmentation_score`
- `num_noise`
- `final_num_clusters`
- `total_clusters_merged`

### 阶段 4：扩展实验

只有在基础 sweep 没给出清晰答案时才允许进入。

允许实验的变量：

- `PCA`
- `allow_single_cluster`

不允许默认进入的变量：

- UMAP
- BERTopic
- 分块聚类
- 新依赖驱动的更重流程

## 结果判读规则

不要只看一个总分。

每轮实验至少同时回答下面三个问题：

1. 本来该在一起的文件，是不是被拆开了？
2. 本来不该在一起的文件，是不是被硬并了？
3. 噪音文件是不是明显变多了？

如果一个方案只是让簇数变少，但误并明显变多，它应当被判为失败。

如果一个方案只是让噪音变少，但靠的是把边界文件粗暴塞进大簇，它也应当被判为失败。

## 默认参数晋升门槛

任何新的默认参数，必须同时满足下面这些条件。

### 必须条件

- 在代表性验证集上优于当前默认值
- 回归集不能出现明显退步
- 对抗集不能新增明确误并

### 量化门槛

建议采用下面的硬门槛：

- `fragmentation_score` 下降，或者至少不高于当前默认值
- `num_noise` 不能明显恶化
- 文件级人工复核中，不能新增高置信度误并
- 至少在 `2/3` 的代表性目录上表现不差于当前默认值

### 否决条件

出现任一情况，禁止晋升默认值：

- 回归集里明显把已知正确案例打坏
- 对抗集里出现新的高置信度误并
- 只能在 `docs/test/valid` 上表现更好，真实目录上没有改善

## 维护规则

### 什么时候新增样本

出现下面任一情况，就应该补样本：

- 新发现了一类稳定失败模式
- 一次重构打坏了旧行为
- 新支持的文件类型带来了新的聚类噪声

### 什么时候删除样本

原则上不删除。

只有在下面两种情况下允许删除：

- 样本已经损坏且无法恢复
- 样本被证明长期误导评估目标

删除时必须写清理由。

### 谁可以改标签

任何人都可以提议，但默认要经过人工复核。

最低要求：

- 改标签的人必须说明原因
- 复核人必须确认这不是为了“让新参数看起来更好”

## 当前最务实的落地方式

如果现在就开始执行，建议按这个顺序建：

1. 把 `docs/test/valid` 明确定义为回归集
2. 增加 `3` 个代表性真实目录
3. 增加 `1` 个小型对抗集
4. 先给每个目录补 `manifest.json`
5. 之后所有 A/B 和参数 sweep 都按这份规范跑

## 结论

`docs/test/valid` 是练习题，不是总决赛。

这份规范的核心不是把验证做复杂，而是强迫我们分清：

- 哪些样本用来防退步
- 哪些样本用来定默认值
- 哪些样本用来专门打脸
