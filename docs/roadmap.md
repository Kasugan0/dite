# 路线图

本文档描述 DITE 当前仍然值得继续推进的方向。它不是历史记录，也不是对所有事项都会实现的承诺。

当前行为的事实来源仍然是 `src/` 下的代码。本文件的作用，是在对照 `docs/archive/` 中的旧设计之后，说明哪些方向今天仍然值得规划，哪些应该延期，哪些不该继续当主线。

## 规划原则

这些原则不是理论偏好，而是当前实现已经证明过的现实结论：

- 保持 CLI-first 的产品形态。
- 除非是明确且有理由的用户可见变更，否则尽量保持向后兼容。
- 优先使用“直接提取内容 + 直接 embedding”，不要默认把系统推回分析层驱动。
- PDF 提取质量和缓存正确性，优先级高于继续扩张表面功能。
- 不要把缓存复用包装成假的“增量聚类能力”。
- 优先收紧现有系统，而不是继续堆用户可见功能。

当前有一个明确例外：

- 聚类 V2 重构允许破坏现有聚类输出、默认参数和部分配置语义。
- 这个例外不是“想改就改”，而是因为当前聚类主路径的数据结构和决策边界已经不足以继续靠小修小补维持。
- 具体方案见 `docs/clustering-v2.md`。

## 当前代码已经证明的方向

这些方向已经被当前实现验证过，应该被当成稳定设计方向，而不是开放问题：

- 文本优先，VLM 作为质量回退。
- HDBSCAN 作为主聚类算法。
- 对部分噪音点做可选的 k-NN 修复。
- 使用 SQLite 做分层缓存，而不是引入向量数据库。
- 在昂贵工作之前先做文件哈希折叠。
- 整理行为保持保守：先预览，支持脚本导出，直接执行也走复制、校验、再删除。
- 并发能力已经存在，后续应该扩展和调优，而不是把它重新包装成一个独立框架。

## 从旧设计里得到的现实教训

archive 里最重要的教训，不是“应该再做更多功能”，而是下面这些：

- 直接 embedding 比默认引入语义分析层更稳更实用。
- 缓存、提取、聚类后处理这些底层边界，比展示层新功能更容易决定系统质量。
- 很多被写成“增量”“异步”“增强”的内容，实际上最后都落回了缓存复用和运行时调优。
- 安全功能值得保留，但不代表它们一定要先于所有系统收口工作落地。

## 当前主线

当前主线不是继续堆新功能，而是先把现有系统收紧、看清、稳住。

这意味着近期重点应该放在：

- 澄清真实行为
- 收紧实现边界
- 提高可观测性
- 清理历史误导

而不是立刻扩张更多用户可见表面。

## 近期优先事项

这些是当前最站得住的下一步方向。

### 1. 更好的缓存可观测性

为什么重要：

- 缓存复用是当前 DITE 最实用的性能能力之一。
- 现在的 `cache status` 虽然有用，但粒度仍然偏粗。

什么叫完成：

- 更清楚地展示单次运行中的缓存命中情况。
- 明确区分路径命中、哈希复用、VLM 复用、embedding 复用。
- 更清楚地显示 stale embedding 和重复文件折叠效果。

它不应该变成什么：

- 一套沉重的指标系统
- 一个独立监控服务

当前仍待拍板：

- 这些统计信息应该持久化累计，还是只在单次运行时输出

### 2. 提取与聚类行为校准

为什么重要：

- 当前系统最复杂的区域不是 CLI，而是提取决策、缓存写回和聚类后处理。
- 这些地方一旦行为模糊，文档、测试和用户认知就会继续漂移。
- 当前已知问题之一，是一些理应归为同一簇的文件会被拆成多个簇；后面的同名现象只是这个问题的症状之一。

什么叫完成：

- 继续收紧 PDF 提取与回退边界。
- 把缓存命中、哈希复用、VLM 选择、embedding 失效逻辑讲清楚并锁定。
- 明确哪些行为是设计选择，哪些只是当前实现结果。
- 明确拆簇问题应该先从哪里修：提取质量、embedding 输入、HDBSCAN 参数，还是更晚的后处理。
- 把“重复簇名”当成聚簇误差的信号，而不是把命名后合并当成默认主解法。
- 为当前小簇级再合并补足明细观测，而不只看总合并数。
- 先验证 embedding 混入文件名是否在真实目录上拉偏结果，再决定是否继续改默认聚类策略。

它不应该变成什么：

- 一次性的大重构
- 为了理论优雅而破坏现有用户行为

当前这条主线的更具体拆解，见 `docs/clustering.md`。

### 3. 现有系统的质量收口

为什么重要：

- 当前更需要把“已经存在的能力”讲清楚、测清楚、稳定下来，而不是继续扩功能面。

什么叫完成：

- 文档、实现、测试三者尽量对齐。
- 已知的误导性说法继续清理。
- 明确哪些旧设计已经废止，哪些只是延期。

它不应该变成什么：

- 重写整个项目
- 借“清理”之名偷偷引入新系统

## 延期但保留的候选

这些方向并没有被否定，但现在不进入主线。

### 可撤销的整理执行

当前状态：

- 延期

为什么延期：

- 它是安全能力，不是无价值能力。
- 但当前还有更重要的事情，也就是先把现有系统边界和行为收紧。

重新进入主线的条件：

- 当提取、缓存、聚类和文档体系已经足够稳定时，再回来做这件事更合理。

### 长文档分块

为什么可能有意义：

- 一些超长文档或多主题文档，用单一最终文本表示时，可能聚类效果不够理想。

为什么现在不该默认推进：

- 当前直接 embedding 路径明显更简单。
- 分块会同时抬高提取、embedding、聚类、命名、缓存和报告的复杂度。
- 当前仓库里还没有足够证据证明它是常规场景所必需的。

更合理的触发条件：

- 只有当真实长文档误聚类案例反复出现，而且无法用更简单的提取质量改进解决时，才应该提高优先级。

### Watch 模式

为什么可能有意义：

- 对下载目录或收件箱式目录来说，持续监听可能是一个真实工作流。

为什么现在不该默认推进：

- 后台持续运行比显式 CLI 调用风险更高。
- 文件监听、自动移动、缓存交互会明显扩大支持面。

更合理的触发条件：

- 只有当确实存在“常开自动整理”场景时，才值得推进。

### 更丰富的运行时并发能力

为什么可能有意义：

- 大目录仍然可能在提取、VLM 和命名阶段遇到延迟瓶颈。

为什么它不是全新功能：

- 当前代码已经有受限并发的提取能力。
- 当前代码已经有受限并发的 VLM 请求和簇命名请求能力。
- 所以后续工作更像是调优与扩展，而不是从零建一个并发子系统。

更合理的触发条件：

- 只有在缓存复用和当前 worker 参数调优后，仍然存在明确瓶颈时，才值得继续深入。

### 多提供商支持

为什么可能有意义：

- 当前 DITE 主要围绕一个 OpenAI-compatible 客户端路径组织。
- 本地模型、成本控制或部署可移植性，都可能让多提供商支持变得有价值。

为什么现在不该默认推进：

- 提供商抽象会同时扩散到 embedding、VLM、chat、配置和错误处理层。
- 当前 OpenAI-compatible 路径已经间接覆盖了不少后端。

更合理的触发条件：

- 只有当当前兼容层真的成为阻塞时，才应当提高优先级。

### 模板化整理

为什么可能有意义：

- 无监督聚类适合“发现结构”。
- 但某些稳定领域最终可能需要“套用确定性目录结构”，例如发票或论文。

为什么现在不该默认推进：

- 这会把产品从“发现结构”推向“应用模式”。
- 字段提取质量会变成新的核心依赖。

更合理的触发条件：

- 只有当无监督聚类对目标工作流明显不够时，才值得进入主线。

## 当前不作为主线方向的内容

下面这些东西当前不应该驱动主线规划，除非以后出现了新的证据。

### 语义分析器成为默认主路径

原因：

- 旧设计自己就已经逐步从这个方向退开了。
- 当前代码已经证明“直接提取 + 直接 embedding”在复杂度和成本上更划算。

`analyzer` 模块可以保留作实验，但不应被当成默认未来。

### 图片重命名

原因：

- 它会引入另一类不可逆的用户可见操作。
- 它和整理有关，但并不是当前产品价值的核心。

### Prompt 管理作为一级子系统

原因：

- 当前 prompt 面还很小。
- 没必要在仓库内部再造一个 prompt 管理产品。

### 把异步处理当成独立主题

原因：

- 旧设计把异步处理写成了未来里程碑。
- 但当前运行时已经存在实际可用的并发控制。
- 后续如果做，也应当视为运行时调优，而不是独立产品主题。

### 假想中的“增量聚类”

原因：

- HDBSCAN 仍然是批处理式聚类步骤。
- 缓存复用是真实能力，但那不等于真正的增量学习。

### 基于 Hidden States 的研究路线

原因：

- 研究上有意思。
- 但离当前部署模型和产品范围太远。

### HTML 报告导出

原因：

- 现阶段不值得进入主线。
- 终端输出、JSON 输出和脚本导出已经覆盖了更核心的需求。
- 它更像展示层扩张，而不是当前系统最急需补强的地方。

## 仍需产品判断的开放决策

这些问题，当前代码没有替你回答，旧设计也没有资格替你拍板。

### 1. 拆簇问题的主修复方向

当前现实：

- 当前主路径是“每个文件产出一份最终文本，再生成一个 embedding，再交给 HDBSCAN”。
- 默认聚类参数是 `min_cluster_size=3`、`min_samples=2`、`cluster_selection_epsilon=0.25`、`cluster_selection_method="eom"`。
- k-NN 修复只处理噪音点，不会把两个已经成形的非噪音簇重新并回去。
- 当前已经有一轮受限的小簇级再合并，但它只覆盖 source 小簇，只看簇质心。
- 同名簇合并发生在命名之后，而且当前 CLI 明确关闭它。

待决问题：

- 短期内，我们是否应该继续把重复簇名当成“拆簇告警信号”，而不是重新把同名合并推回默认路径？
- 中期内，拆簇问题应当优先从哪一层下手校准：提取质量、embedding 输入形式、HDBSCAN 参数，还是新增第二阶段簇间合并策略？

### 2. 提供商策略

待决问题：

- “只要求 OpenAI-compatible” 到底是有意为之的产品边界，还是暂时的实现捷径？

### 3. 分块要推进到什么程度

待决问题：

- 分块应该只作为处理真实长文档失败案例的修补手段，还是应该升级成带有自己缓存与报告语义的一等流水线模式？

## 当前建议的执行顺序

如果没有新的产品约束，更务实的顺序是：

1. 更好的缓存可观测性
2. 提取与聚类行为校准
3. 现有系统的质量收口
4. 再评估长文档分块、更强的运行时并发能力、多提供商抽象和 Watch 模式是否真的有真实需求

## 它和 archive 的关系

`docs/archive/` 依然保留为历史设计材料和想法仓库。

但现在的分工应该是：

- 当前代码决定“什么是真的”
- 本路线图决定“什么还值得规划”
- archive 不再自己决定优先级

如果需要更明确地解释 archive 应该怎么读，请看 `docs/archive-review.md`。
