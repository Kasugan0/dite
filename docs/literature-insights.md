它不是相关工作列表。相关工作入口见 `docs/related-work.md`。

这里的目标只有一个：

- 每读完一篇真正相关的论文或官方技术资料，就把它对 DITE 的具体启发写下来

记录原则：

- 每篇单独成节
- 不复述摘要

## 总启发与下一步设计

把这 11 篇文献连起来看，DITE 当前聚类问题的根因已经非常清楚：我们过去把“文档聚类”错误地简化成了“对最终文本做一个 embedding，再交给 HDBSCAN”。这个假设在小样本、近重复文档、标题高度一致的场景里还能凑合，但一旦进入真实文件目录，它就会立刻暴露出结构性缺陷。HDBSCAN 主论文、FAQ 和 DBCV 共同说明，密度聚类不是万能裁判，它只适合在一个已经比较像密度空间、而且维度和噪音水平都可控的表示上抽取稳定簇；它不负责自动修复糟糕的数据结构，也不应该被迫承担主题理解、近重复识别、边界裁决和异常修补这四种不同职责。SBERT 和 BERTopic 则进一步说明，embedding 的合理位置是“召回层”和“主题空间基础设施”，而不是系统里唯一的最终真相；真正成熟的路线，应该把 embedding、降维、聚类、表示和解释分开。LayoutLMv3 与多模态文档聚类论文又把另一个事实讲透了：对文档来说，正文语义从来不是唯一信号，版式、视觉、标题层级、模板结构在很多真实场景里本来就是语义的一部分，而且不同模态会在不同噪声条件下失效，因此不能简单粗暴地拼到一个大向量里。LITA、NER 特征聚类和约束聚类这几篇则给出第三层启发：LLM、实体、must-link / must-not-link 这些东西不该只当“分析附属品”或“测试注释”，而应当成为正式系统语言的一部分，分别承担边界裁决、对象去歧义和关系约束的角色。

因此，下一步的设计要求已经可以明确写死，而不需要再停留在“可能这样也可能那样”的模糊阶段。第一，DITE 必须从“单向量文件对象”升级成“多视图文档对象”。每个文件至少要显式区分正文内容、文件名、路径、扩展名、标题候选、提取质量、摘要、关键词、主题、领域、布局提示等字段，不能再把文件名偷偷混进正文 embedding 里假装一切都是语义。第二，聚类流水线必须分层，最少拆成四层：输入净化、强连接召回、主题聚类、边界裁决与簇表示。输入净化负责识别弱提取、短文本、文件名主导等污染源；强连接召回负责找出近重复、强 must-link 候选和高相似对；主题聚类负责在整理过的表示空间里抽取稳定团块；边界裁决与簇表示层则负责用更贵但更强的模型处理模糊关系并生成可解释结果。第三，LLM 不再被定义为“簇命名器”，而应当被定义为“受预算约束的表示器与保守仲裁者”。它不应该全量处理全部文件，而应该只介入少数模糊样本、小簇合并争议和最终簇解释。第四，约束信息必须升格。`must_link`、`must_not_link`、实体共现、标题模式、文件名规则都应当成为正式评估与裁决接口，而不是留在文档里供人肉 eyeballing。第五，评估体系必须重写，未来不能再只看簇数、噪音数和合并数，而要同时拥有过程指标、密度类内部指标和外部约束指标。

基于这些文献，下一步不应直接跳到代码实现细节，而应先完成三份设计性产物。第一份是统一的数据结构定义，明确 `DocumentFeatures`、`ClusterRepresentation`、`CandidateEdge`、`AdjudicationDecision` 这些核心对象各自包含什么字段、由哪一层生产、由哪一层消费。第二份是新的流水线契约，明确每一层的输入、输出、失败语义、缓存边界和可观测性要求，避免未来再出现“一个补丁函数偷偷承担主路径责任”的坏味道。第三份是新的评估协议，正式定义 V2 应该报告哪些指标、哪些必须来自代表性验证集、哪些必须来自对抗集、哪些约束会直接阻断某类合并。只有这三份设计先立住，后续代码实现才不会重新滑回“继续调 HDBSCAN 参数”和“继续堆更多后处理补丁”的老路。换句话说，文献已经把方向讲得足够清楚了：DITE 的下一阶段不是更换某个模型，而是承认文档聚类本质上是一个多信号、分层决策、带约束和带解释的系统工程。

## 1. HDBSCAN 主论文

这篇论文给我的最大启发，不是“继续用 HDBSCAN”，而是“终于看清 HDBSCAN 在 DITE 里本来应该扮演什么角色”。当前 DITE 把 HDBSCAN 当成主语义裁判：文件提取完，做一个 embedding，然后直接丢给 HDBSCAN，指望它同时完成主题发现、重复吸附、边界切分和噪音处理。这个使用方式太贪心了，甚至可以说是误用。主论文真正强调的，是它先构造一个完整的 density-based hierarchy，再从这个层次结构中提取一个平面解；而这个平面解的核心目标不是“让每个语义关系都自动正确”，而是利用簇的 stability 做全局最优的抽取。换句话说，HDBSCAN 的强项是：在一个已经比较像“密度空间”的表示上，稳健地找出不同密度层次下仍然稳定存在的团块。它并没有承诺帮你把所有 heterogeneous signal 自动捏成一个正确的空间。

对 DITE 这次重构最关键的影响有三点。第一，当前“一个高维内容 embedding 承担所有语义决策”的前提应该被推翻。论文告诉我，HDBSCAN 擅长的是从密度层次中抽稳定簇，而不是凭空修复一个糟糕表示空间。因此，V2 必须把 HDBSCAN 降级成某一层的局部求解器，而不是整个聚类系统的唯一中心。第二，论文明确把 outlierness、hierarchy 和 flat clustering 放在同一框架下看，这对 DITE 很重要。今天的 DITE 把噪音修复看成 HDBSCAN 失败后的补锅，但从论文视角看，噪音不是偶发异常，而是模型本来就允许存在的结果；真正要问的是：这些噪音点是因为输入表示差、样本太少、密度不可分，还是因为它们确实不该属于任何稳定簇。第三，论文提到如果有部分标签或 instance-level constraints，可以在后处理时把 constraint satisfaction 和 cluster stability 一起考虑。这一点直接撞上 DITE 已经有的 `must_link` / `must_not_link` 验证方向：这些约束不该只留在测试集文档里，它们未来可以进入正式评估，甚至进入边界判定层。

更具体地说，这篇论文改变了我对 V2 中 HDBSCAN 位置的判断。之前我还把它看成“也许继续保留为主题聚类主引擎”；现在我的看法更保守：HDBSCAN 仍然值得保留，但前提是它只在一个已经过净化、降维、显式分离了元数据污染的空间上工作，而且它解决的应是“稳定主题团块提取”，不是“全量文件理解”。近重复识别、文件名模式、路径上下文、标题候选、实体和 LLM 摘要这些信号，不该指望 HDBSCAN 在单一向量里自己悟出来。论文没有给 DITE 提供现成答案，但它逼着我承认一个事实：如果数据结构不对，再好的密度聚类也只是把错误更稳定地输出出来。这一点，对当前 DITE 来说非常致命，也非常有价值。

## 2. HDBSCAN FAQ

如果说主论文告诉我 HDBSCAN 的理论定位，那么 FAQ 则把 DITE 当前工程实现的问题直接钉死了。它最大的价值，不在于新理论，而在于非常明确地划出了“你什么时候不该怪 HDBSCAN，什么时候其实是你输入空间或参数假设错了”。对 DITE 来说，最关键的结论有四个。第一，高维退化不是边角提醒，而是当前系统的核心风险。FAQ 明说 HDBSCAN 在低到中维数据上通常表现不错，但维度升高后性能会显著下降，经验上大概到 50 到 100 维还能比较稳，再往上就不再有保障。DITE 现在直接拿 4096 维 embedding 跑 HDBSCAN，这基本等于把算法放进它官方自己警告过的危险区里。之前我还能把“直接高维聚类”看成一种可继续调参优化的工程路线；看完 FAQ 之后，这种想法应该结束了。V2 如果还保留 HDBSCAN，就必须先引入降维、重表示或图结构，而不是继续在原空间里硬调 `epsilon`、`min_samples` 和 `min_cluster_size`。

第二，FAQ 对 `min_samples` 的解释，直接暴露了 DITE 当前“噪音修复心态”的问题。官方说得很朴素：大部分点被判成噪音，首先看 `min_samples`，默认它会等于 `min_cluster_size`，调低会减少噪音，但也有极限，因为你的数据可能本来就 noisy。翻译成 DITE 的话就是：噪音不是默认错误，而是参数和数据共同作用下的正常输出。当前 DITE 把噪音修复做成一个后置补丁，容易给人一种错觉，好像“噪音越少越好，修得越多越对”。FAQ 实际上提醒我，噪音应该被当成诊断信号：如果系统频繁产生噪音，应该先回头看表示空间、样本规模和密度可分性，而不是先写更多修复逻辑。第三，FAQ 对 `leaf clustering` 的说明也很重要。它说如果得到一个大簇加少量离群小簇，说明你的数据整体像一个大团块；想挖更细粒度结构，可以用 `leaf clustering`。这直接说明“想要更细粒度”是一个有代价的选择。DITE 当前正好相反：它主要问题不是一个大团块，而是被切碎成很多小簇。因此 FAQ 其实从反面支持了我们的判断：现在不应该往更细粒度方向推，而是该先处理过碎和表示污染。

第四，`approximate_predict()` 的存在改变了我对边界文件归属的看法。FAQ 说明，开启 `prediction_data=True` 之后，可以把新点分配到已存在的簇，但不会生成新簇。这和 DITE V2 想要的“先建稳簇，再给边界文件做保守归属”非常契合。也就是说，未来的系统不一定非要靠 k-NN 去修噪音；完全可以先建立稳定核心簇，再对边界点采用近似预测、soft assignment 或后续裁决层。这比现在的“聚完以后一锅端修噪音”更像一个有层次的系统。总的来说，FAQ 这篇资料给我的启发非常直接：DITE 的问题并不是 HDBSCAN 参数还没调精，而是我们让它在错误的表示空间里承担了太多职责。V2 必须把高维直接聚类降级为历史路线，把噪音从“错误结果”改回“诊断信号”，并认真考虑“核心簇先行、边界点后分配”的分层结构。

## 3. DBCV

DBCV 这篇文献的启发非常直接：它让我意识到，DITE 当前关于聚类质量的很多讨论，其实还停留在“结果看起来像不像”“簇数多不多”“噪音高不高”这种半经验状态。对于一个明确保留了 HDBSCAN、噪音点、小簇合并、未来还可能引入图聚类和多模态表示的系统来说，这种评估方式太原始了。DBCV 的出发点非常对症：传统相对有效性指标大多偏向球状簇或 globular clusters，当数据天然包含任意形状、低密度分隔、甚至噪音对象时，这些指标会失真。而 DITE 当前面对的文档集合，恰恰就更接近这种情况。学习资料、版本副本、扫描 PDF、短文本、说明文档和论文混在一起，本来就不是一堆干净、均匀、球状的团块。继续用只看总簇数或均值化摘要的办法去评价这种结果，本质上是在用错误的尺子量错误的问题。

这篇文献改变了我对 V2 评估体系的理解。之前我更倾向于“多补 must-link / must-not-link 和人工标注就够了”，现在看这还是不够。外部约束当然重要，但如果没有一个更像 density-based clustering 自己语言的内部指标，我们很难比较不同表示空间和不同聚类阶段设计。例如，V2 里如果我们实验 `PCA/UMAP -> HDBSCAN`、图社区发现、近重复召回后再主题聚类，这些方案不一定都能直接拿相同的簇数、噪音数来判断优劣。DBCV 至少提供了一种方向：评价 should focus on within-cluster density connectedness and between-cluster density separation，而不是一味问“有没有形成紧凑球状中心”。对 DITE 来说，这尤其重要，因为未来某些簇可能是“主题上相连，但内部格式跨度很大”的文档族群；只看传统聚类紧凑度，很可能会错误惩罚这种用户真正想要的簇。

更重要的是，DBCV 逼着我重新定义 DITE 的实验报告应该长什么样。现在的 `scan` JSON 和实验脚本更像诊断面板：初始簇数、最终簇数、噪音数、小簇合并数。这些字段当然仍然要保留，因为它们解释过程。但如果 V2 真要成为一个可以晋升默认策略的大重构，就必须把“过程统计”和“质量指标”分开。过程统计回答“系统做了什么”，质量指标回答“系统做得是否更好”。DBCV 对我最大的启发就是：不能继续把这两件事混在一起。未来的 `validation` 和 `experiments` 应该至少同时包含三层指标：一层是过程层，例如候选边数量、LLM 判定次数、文件名主导比例；一层是内部聚类层，例如 DBCV 或其他密度友好指标；一层是外部约束层，例如 must-link recall、must-not-link violation 和 fragmentation per cluster_id。只有这样，我们才能避免出现一种常见幻觉：小簇少了，所以结果一定更好；或者噪音少了，所以系统一定进步了。DBCV 让我更确信，V2 的评估不能再靠肉眼和摘要数字凑合，它必须拥有真正匹配密度类聚类任务的内部验证语言。

## 4. SBERT

SBERT 这篇论文对 DITE 的启发，远不只是“换个更好的 embedding 模型”。它真正改变我判断的地方，是它把两种经常被混在一起的能力彻底拆开了：一种是可以离线预计算、适合大规模相似度搜索和聚类的 sentence embedding；另一种是需要把两个文本一起送进模型、虽然更细致但计算代价极高的 pair modeling。论文开头给出的对比非常关键：原始 BERT 在 sentence-pair 任务上很强，但如果要在一个包含 10000 个句子的集合里两两找最相似对，会产生巨大的推理开销，而 SBERT 通过 siamese/triplet 结构得到可直接比较的向量，把这个过程从几十小时压缩到几秒。这对 DITE 的价值不是性能数字本身，而是它告诉我们一个架构事实：**适合做全局召回的模型，和适合做局部精判的模型，不必是同一种调用方式。**

这件事直接打到了 DITE V2 的核心。当前 DITE 把“embedding 很有语义”误用成了“embedding 足够负责最终分簇”。SBERT 论文恰恰说明，embedding 的真正优势在于把文本投到一个可以高效比较的空间里，从而支撑 semantic search、clustering、nearest-neighbor retrieval 这类全局操作。它并没有说 cosine 相似度就等于最终聚类真相，更没有说可以跳过第二阶段判定。换句话说，SBERT 最像 DITE V2 中的“候选边生成器”和“强连接召回层”，而不是最终裁判。对 DITE 来说，这非常关键，因为我们现在最缺的不是一个更玄学的全能聚类器，而是一层稳定、便宜、可批量运行的语义召回基础设施：它负责告诉系统“这些文件值得彼此比较”，但不独自决定“它们最终一定属于同一簇”。

SBERT 还让我更清楚地认识到当前 DITE 在数据结构上的单薄。论文强调的是 sentence embeddings，核心是把文本编码成可比较向量。但 DITE 当前文件对象里除了最终文本和 embedding，几乎没有别的正式一等公民信号。文件名、路径、扩展名、标题候选、关键词、摘要、版式信息都没有被清晰地放进结构里。这意味着哪怕我们把 embedding 模型换成再好的 SBERT 类模型，也只是把“单一表示空间承载全部关系”这件事做得更顺滑了一点，而不是从根本上解决问题。真正值得学习的是 SBERT 的角色定位：它非常擅长为海量对象建立一个初始语义邻接图，这正好能成为 DITE V2 中“强连接召回”的基础。比如，同一主题但不同格式的文件、重命名后的近重复文件、内容接近但标题不同的课程资料，应该先通过 embedding 拉出候选邻居，再交给后续层结合元数据和 LLM 做保守精判。

因此，这篇论文让我对 V2 的一条关键设计更有把握：embedding 层要继续保留，而且要做得更正规，但它的职责必须降级并明确。它负责的是召回、近邻、候选边和初步社区，不负责单独给出最终文档族群。未来如果 DITE 引入 cross-encoder 或 LLM 判定层，它们和 SBERT 并不是竞争关系，而是天然上下游关系：SBERT 负责缩小搜索空间，后者负责对少量模糊关系做更贵但更可靠的决策。换句话说，SBERT 教会我的不是“继续信 embedding”，而是“终于知道应该只在该信的地方信它”。

## 5. BERTopic

BERTopic 这篇论文对 DITE V2 的价值，不在于“我们要不要把 BERTopic 搬进来”，而在于它提供了一个非常干净、几乎可以直接翻译到 DITE 上的结构分层。此前我对 DITE 重构已经有一个直觉：不能再让单个 embedding 和一个 HDBSCAN 扛住所有任务。但 BERTopic 真正让我把这个直觉变成了清晰的系统边界。它最重要的设计不是某个具体算法细节，而是它公开承认 topic modeling 不是单步操作，而是至少包含这些相对独立的阶段：文档 embedding、降维、聚类、token weighting、topic representation。这个拆分非常关键，因为它等于公开否定了“一个向量 + 一个聚类器 + 一个簇名”就足以得到稳定主题结构的想法。对 DITE 来说，这几乎就是当前架构问题的反面教材。

这篇论文最直接改变了我对 DITE V2 “阶段设计”的判断。之前我主要从工程症状出发，把 V2 想成“强连接召回 -> 主题聚类 -> 边界判定 -> 簇表示”。BERTopic 则从 topic modeling 的角度告诉我，这种拆分不仅合理，而且是成熟路线。特别是它把 dimensionality reduction 放在聚类之前这一点，对 DITE 尤其有价值。当前系统一大问题就是直接在高维 embedding 上跑 HDBSCAN，而 BERTopic 的默认心智模型恰恰是：高维语义表示很好，但不代表它天然适合聚类；因此需要一个中间步骤把空间整理成更 cluster-friendly 的形式。对 DITE 而言，这直接支持 V2 中把“降维或图结构整理”正式引入主实验路线，而不是继续把它当扩展实验的次要选项。

BERTopic 还让我重新理解了“主题表示”在 DITE 中的地位。当前 DITE 在聚类之后只做一件很弱的事：给簇命名。看起来好像和 BERTopic 里最后的 topic representation 很像，但其实差得很远。BERTopic 的簇表示不是 cosmetic label，而是一个正式阶段：它通过 c-TF-IDF 和后续表示模型，把聚出来的簇重新投射回可读、可解释的词和主题结构。翻译成 DITE 的语言，就是“聚类结果需要一个独立的解释层”。这直接支持我之前的判断：V2 不应该只生成 `name`，而应该为每个簇生成完整的 `summary / keywords / topic / domain / evidence`。如果没有这层，用户看到的就仍然只是一个漂亮但可能误导的标签，而不是足以支撑人工复核和后续整理的簇表示。

最后，这篇论文还在方法论上帮我避免一个陷阱：不要把 BERTopic 当成“topic modeling 软件”，而应该把它当作“模块化聚类与表示流水线”的范例。DITE 的对象不是纯文本短文，而是文件级文档集合，里面混着 PDF、Markdown、PPTX、课件、论文、说明文档。因此我们不可能生搬 c-TF-IDF 或它的整个输出形式。但它所强调的 modularity 几乎可以原样继承：embedding 模型可以换，降维可以换，聚类器可以换，表示模型可以换。对 DITE V2 来说，这意味着我们不该再把聚类写成一个单函数里的一串固定动作，而是要把“候选边生成、主题空间整理、聚类、簇表示、边界裁决”设计成可以替换和对比的阶段。BERTopic 不是 DITE 的最终答案，但它让我更确信：V2 最核心的改动不是换模型，而是承认系统必须分层。

## 6. BERTopic algorithm / representation docs

BERTopic 的官方 algorithm 和 representation 文档，比论文本身更直接地影响了我对 DITE 实现细节的判断。论文给了正确方向，但文档把一件事说得更彻底：**LLM 在成熟流水线里最稳的位置，是表示层，而不是基础聚类层。** algorithm 文档清楚地把整个流水线拆成 `embeddings -> UMAP -> HDBSCAN -> tokenization -> c-TF-IDF -> representation_model`。这个顺序非常重要，因为它说明表示模型是建立在已经形成的 topic/cluster 之上的。也就是说，文档世界里的 BERTopic 并不是“先让 OpenAI 想主题，再去分组文档”，而是“先形成簇，再用更适合解释的模型来丰富这些簇的表示”。这点几乎可以直接拿来修正 DITE 当前和未来的 LLM 用法。

对 DITE 来说，这个启发特别扎实。当前系统里 LLM 只参与 `cluster naming`，而且是最后才出场。看起来这已经和 BERTopic 的表示层有点像了，但其实还差两大截。第一，DITE 目前的命名输入过于朴素，主要是少量代表文件内容和文件名；而 BERTopic 的表示文档明确展示了更强的输入组织方式，例如 `[DOCUMENTS]` 和 `[KEYWORDS]` 的模板占位。这让我意识到，V2 里的 LLM 不应当直接吃整篇原文，而应当吃一个已经压缩过、结构化过的簇表示候选：代表文件摘要、关键词、标题候选、扩展名模式、路径上下文，必要时再加正文片段。第二，BERTopic 的 representation model 明确支持多种表示模型并存，甚至可以把 KeyBERT、MMR、POS 和 OpenAI 放在一起做 multi-aspect topic modeling。这一点对 DITE 尤其重要，因为它说明“LLM 不是唯一表示源”。V2 完全可以先用便宜且稳定的统计或 embedding 方法生成关键词和候选主题，再把这些结果喂给 LLM 做最后压缩和命名，而不是让 LLM 从零开始猜。

更进一步，这份文档让我对 DITE 的“边界判定层”也更有信心。虽然 BERTopic 主要讲的是 topic representation，不是 cluster adjudication，但它所暴露的思路是一样的：高成本模型应该建立在小规模、已经过筛选的输入之上。OpenAI 表示模型的配置里有 `nr_docs`、`doc_length`、`tokenizer`、`delay_in_seconds` 这些字段，这说明官方自己也把 LLM 当成昂贵且需要预算管理的组件。对 DITE V2 来说，这几乎就是现成的工程原则：LLM 不应该全量处理全部文件；它应该只处理小簇重审、边界文件归属和最终簇表示，而且每次只看少量代表样本。这样做的好处不仅是省钱和稳定，更重要的是可解释。因为一旦输入已经是结构化候选，LLM 的输出就更容易被追溯为“它是在这些证据上做出的判断”，而不是“模型玄学地觉得这几个文件像一类”。

因此，这两份官方文档最终让我把一个此前还带点探索色彩的想法，升级成了 V2 的正式原则：LLM 不是主聚类器，而是“受预算约束的表示器和保守裁判”。它应该处在聚类之后、边界判定和簇解释之中，而不该进入最底层的全量召回。对当前 DITE 来说，这比单纯“继续优化簇命名 prompt”高明得多，也现实得多。因为真正需要升级的不是 prompt 文案，而是 LLM 在整个流水线里的位置定义。

## 7. LayoutLMv3

LayoutLMv3 这篇论文对 DITE 的最大启发，是它让我更坚定地放弃“正文文本是唯一正式信号，版式和视觉最多算附加噪声”这种看法。过去在 DITE 的讨论里，我虽然已经承认扫描 PDF、课件、模板化材料、表单、讲义的版式很重要，但这种承认还停留在工程直觉层面：看起来有用，所以未来也许要纳入。LayoutLMv3 则把这个直觉提升成了更硬的建模判断。它最重要的点，不只是“多模态效果更好”，而是它通过 unified text and image masking 加上 word-patch alignment objective，明确把文本内容、视觉块和两者之间的对应关系视为同一文档表示的一部分。换句话说，对文档 AI 来说，文本和图像不是两个事后拼接的外挂特征，而是天然耦合的结构信号。这对 DITE 非常重要，因为 DITE 聚类的对象不是普通网页句子，而是现实世界里的文件。

这篇论文直接改变了我对 V2 中文档特征结构的边界判断。之前我给 `DocumentFeatures` 里放 `layout_hints`，更多是把它看成一个未来增强项；现在我认为它至少应该成为一等字段，即便第一版实现不一定立刻引入真正的 LayoutLMv3 模型。原因很简单：DITE 面对的很多误聚类，不是“文本语义没提取出来”，而是“文本相似但文档功能完全不同”。例如，同样谈到实验、优化、训练、结果的文件，可能分别是课程讲义、学术论文、项目记录和会议摘要。纯内容 embedding 很容易把它们拉近，但版式、标题层级、表格密度、页面结构、是否像报告/课件/论文/表单，这些信息常常正是用户在脑子里分组时实际在用的信号。LayoutLMv3 论文提醒我：这种信号不是 fancy feature，而是文档理解的核心部分。对 DITE 来说，即便 V2 第一轮不直接接入重模型，也至少应该把布局相关的低成本代理特征正式纳入，例如页数、标题层级、段落密度、表格/图像比重、是否强模板化、文本块统计等。

另外，LayoutLMv3 也让我更谨慎地看待“多模态融合”的实现方式。它的 unified masking 和 word-patch alignment 不是把图像 embedding 和文本 embedding 粗暴拼接，而是用预训练目标去逼模型学 cross-modal alignment。这一点对 DITE 是个重要警告：我们不能因为知道视觉和版式有价值，就把所有模态信号直接塞进一个大向量然后继续硬聚类。那样做大概率只会把原来的问题从“文件名污染正文”升级成“视觉也开始污染正文”。真正值得学习的，是“显式承认不同模态之间存在对应关系和偏置”，然后让系统在后续阶段按角色使用这些信号。对 V2 来说，这意味着版式和视觉信号短期内更适合以 `layout_hints`、`template_signals`、`document_type_priors` 的形式进入，而不是一上来就追求一个统一的超大多模态 embedding。LayoutLMv3 没有直接告诉 DITE 该怎么落地，但它把一个关键判断变得更清楚了：文档聚簇如果长期忽视布局和视觉，只盯正文语义，最终一定会在真实文件场景里撞墙。

## 8. Unsupervised Document and Template Clustering using Multimodal Embeddings

这篇论文是目前所有材料里和 DITE 任务最贴脸的一篇，因为它讨论的根本不是“普通文本聚类”，而是文档级与模板级这两个粒度不同但都很现实的文件组织任务。它给我的最大启发，是逼我彻底放弃“聚类只有一个正确粒度”这种偷懒思维。论文从一开始就把 document-level clustering 和 template-level clustering 分开：前者按大类分，比如发票、身份证、收据；后者在同一文档类型内部继续按模板和版式差异分。对 DITE 来说，这个区分非常重要。当前系统里我们一边抱怨同主题文件被拆碎，一边又默认“更细或更粗都可能是错”，其实缺少的正是这种任务层级意识。用户在某些目录里想要的是主题级聚簇，例如“番茄病害识别相关资料”；但在另一些目录里，他们可能真的想把“不同模板的课程讲义、表单、报告版本”分开。论文告诉我：这不是同一个 objective，不能指望一套单尺度聚类策略自动兼顾。V2 至少应该在内部承认这种层级差异，即便第一版不开放两个用户模式，也要避免把“模板特征”和“主题特征”混成同一个信号。

这篇论文第二个极其重要的启发，是它把“模态 trade-off”说得非常具体，而不是泛泛而谈“多模态通常更强”。它的实验结论很清楚：视觉特征在干净页面上几乎可以直接解决模板发现问题，但一旦遇到 print-and-scan、重度噪声、光照和几何扰动，文本信号又重新成为主要鲁棒来源；融合模型通常在两者之间取得更好的平衡。这个结论对 DITE 简直是当头棒喝。我们现在很容易陷入一种简单叙事：文本不够，就加视觉；视觉再不够，就再上大模型。但论文告诉我，真正的问题不是“哪种模态更高级”，而是“在这个数据分布下，哪种模态更稳”。这直接支持 V2 中“多信号并存，但按质量动态加权”的方向。比如对扫描 PDF，不能默认相信 OCR 文本；但也不能天真地相信视觉一定更稳。系统必须显式知道当前文本质量、图像质量、版式稳定性各自如何，并据此决定信号权重。换句话说，多模态不是“把更多东西拼一起”，而是“承认不同模态在不同失真条件下会失效”。这对 DITE 的提取层、特征层和边界判定层都有直接影响。

第三，这篇论文还给了 V2 一个很实际的后处理和多页文档启发。它使用了 HDBSCAN + k-NN 的 hybrid 作为 practical baseline，同时在后文讨论了多页文档如何通过 page graph、salience-weighted pooling 和 late fusion 来获得更稳定的 document embedding。虽然 DITE 当前还主要按单文件最终文本处理，但这个思路非常重要：如果未来面对真正的多页异质文档，不能简单把所有页文本拼接后做一个 embedding，就假装 document-level semantics 已经被捕获。论文提出的 page-level embeddings + graph smoothing + weighted pooling，至少说明了一个方向：多页文档需要先在页层建表示，再上升到文档层。对 DITE 来说，这也侧面证明当前“每个文件只有一份最终文本”的结构迟早会成为瓶颈。此外，论文提到的 post-clustering consolidation 和 weak/semi-supervised extensions 也让我更确信：边界裁决和约束信息不是多余花活，而是现实系统中迟早要补上的层。总体上，这篇论文对 DITE 的最大价值不是某个模型排行榜，而是它把“粒度分层、模态 trade-off、页级到文档级聚合、后处理必要性”这几件事同时摆到了桌面上。V2 如果忽视其中任何一件，都很可能重演现在这种表面上能跑、实际上碎簇严重的局面。

## 9. LITA

LITA 这篇论文对 DITE 的价值非常高，因为它几乎把我们对 LLM 的直觉用一种更节制、更工程化的方式说清楚了。当前最容易犯的错误，是一看到 LLM 在主题理解上很强，就想让它直接下场接管整个聚类过程；另一种保守过头的错误，则是把 LLM 永远限制在最后起名这一步，完全不参与结构修正。LITA 给出的路线介于两者之间，而且更现实：先用 embedding-based clustering 建立初始结构，然后只识别一小部分 ambiguous documents，让 LLM 去重新分配这些文档到已有主题或新主题中。这里真正重要的不是“迭代 refinement”这个外壳，而是它背后的资源分配原则：**LLM 的预算应该花在最不确定、最有争议、最容易影响最终质量的少数样本上。** 这和 DITE V2 之前形成的“边界判定层”构想几乎完全一致，但 LITA 让我更确信这不是拍脑袋，而是一条有方法论支撑的路线。

这篇论文首先改变了我对 DITE 中 “LLM 是否要进入聚类主路径” 的态度。之前我的表述更像“LLM 不该做全量聚类，但可做边界判定”；LITA 则把这个判断进一步收紧成一种更可执行的策略：不是所有边界问题都交给 LLM，而是先定义哪些文档是 ambiguous，再只让 LLM 处理这些对象。对 DITE 来说，这意味着 V2 里不能只写一个宽泛的“小簇合并裁决”开关，而应该设计真正的 ambiguity detection。比如，某个文件同时与两个簇有相近相似度、某个小簇与多个候选簇都有中等匹配、某个文件在正文语义上像 A 簇但在文件名/路径/版式上又像 B 簇，这种案例才应该进入 LLM 判定队列。换句话说，LLM 不是后处理里随时可用的万能专家，而是“只出现在高价值纠纷点上的仲裁者”。LITA 正是用这种思路控制了 API 成本，同时提升了 topic quality。对 DITE 这种本地文件工具而言，这个思路尤其关键，因为一旦把 LLM 放得太前、太宽，系统立刻会变成又慢又贵还难复现的怪物。

第二，LITA 让我更重视“初始聚类不需要完美，但必须足够好到能暴露模糊样本”这一点。当前 DITE 的一个隐性问题是：初始聚类碎得太厉害，导致后处理几乎什么都能被定义为“模糊”，最后反而没有重点。LITA 的逻辑恰恰相反：先用便宜方法打底，得到一个可工作的初始主题结构，再针对最有问题的少数文档迭代细化。翻译成 DITE 的工程含义，就是 V2 不能跳过前面的表示净化、强连接召回和主题聚类整理，直接把残局扔给 LLM。只有当初始空间已经把大多数明显关系处理得差不多了，LLM 才能真的发挥“高价值局部修正”的作用。否则它只是被迫替一个烂基础设施兜底。这篇论文因此也间接支持了我们之前对 `DocumentFeatures`、候选边和分层聚类的坚持。

最后，LITA 还让我开始把“LLM 预算”视为 V2 的正式设计参数，而不是实现细节。论文从一开始就把高 API 成本当作核心约束条件，这一点非常重要。DITE 的文档理解任务虽然不像开放域 topic modeling 那样规模巨大，但只要进入真实目录，文件数量同样可能迅速膨胀。如果没有预算意识，任何“让 LLM 多参与一点”的想法最终都会变成不可维护的默认路径。因此，这篇论文直接推动我把 `cluster_adjudication` 配置想得更具体：应该有进入 LLM 层的候选数量上限、每个簇允许选择的代表样本数、置信度阈值、是否允许新簇提议、失败回退路径等。总的来说，LITA 的最大启发不是它比 BERTopic 更强，而是它把一个对 DITE 极其关键的设计原则具体化了：LLM 不应该均匀地撒在整个系统里，而应该集中打击最难判、最贵但也最值得判的少数样本。

## 10. Semantic Document Clustering on Named Entity Features

这篇论文虽然老，而且方法从今天看并不复杂，但它对 DITE 的启发反而非常干净：它迫使我承认“named entities、类型、标识符这些信息，本来就可以是独立聚类视图”，而不是只有在大模型时代才有资格进入系统。当前 DITE 的一个潜在陷阱，是我们一边想在 V2 里加入 `summary / keywords / topic / domain / entities`，一边又很容易把这些东西想成必须由 LLM 才能生产、必须由 LLM 才能理解的高级语义。可这篇论文恰恰说明，即使在一个相对传统的向量空间框架里，只要把实体名、实体类型、name-type pair、identifier 等结构化信息单独拿出来，它们就已经足以显著改变文档之间的关系。对 DITE 来说，这个提醒非常重要：实体不是“正文 embedding 的附属说明”，而是能够独立定义文件语义边界的侧信息。

更具体地说，这篇论文改变了我对 `DocumentFeatures` 中实体与元数据字段地位的判断。之前我把 `keywords / entities / domain` 更多看成 LLM 摘要层输出的一部分，主要作用是帮助簇表示和小簇合并。读完这篇之后，我更倾向于把其中至少一部分提升成“聚类前信号”。因为很多文件的主题边界，恰恰就体现在对象层面，而不一定体现在整篇文字的平均语义上。例如，两篇都在讨论某种“优化”“训练”“系统设计”的文档，正文 embedding 可能会很近；但如果一篇 repeatedly 提到番茄、病害、YOLO、叶片，另一篇 repeatedly 提到 Minecraft、模组、服务器、Fabric，它们的人类可感知差异首先就是实体和术语集合。换句话说，实体视图有能力对正文 embedding 做去歧义，这正是 DITE 目前最缺的。更现实一点说，文件名、标题和摘要里出现的人名、机构名、课程名、软件名、模型名，本来就应该被系统单独建模，而不是期待 embedding 自己平均后还能保住这些边界。

这篇论文还让我更愿意接受“多视图不一定意味着复杂神经网络”。当前我们在讨论 V2 时，很容易被多模态、多阶段、LLM、cross-encoder 这些词带偏，以为只有上重武器才算认真重构。但这篇工作其实给了一个很务实的提醒：就算不用最先进的模型，把文档从单一词袋或单一正文表示，升级成几个彼此可解释的 feature spaces，本身就已经是结构升级。对 DITE 来说，这意味着 V2 第一轮完全没必要等到“完美的实体抽取器”或“全量 LLM 文档分析器”成熟后再开始。哪怕只是从文件名、标题候选、正文前若干行和简单规则中提取出高频术语、命名实体或标准化对象名，再把这些结果作为独立特征纳入候选边和边界判定，也已经比当前的单向量路线更有解释力。简而言之，这篇论文给我的最重要启发不是方法本身多先进，而是它把一个常被忽略的事实重新摆回桌面：对于文档聚类，实体和对象往往就是语义的骨架。DITE V2 如果不把它们作为正式信号来处理，就仍然会在“主题接近但对象不同”或者“对象一致但表述分散”的场景里继续犯错。

## 11. Pairwise constraints / constrained clustering

这一组关于 pairwise constraints 和 constrained clustering 的材料，对 DITE 的启发并不是“我们下一步要把系统改造成半监督聚类器”，而是它们让我重新定义了 `must_link / must_not_link` 在项目里的地位。当前 DITE 的 `validation` 文档里已经有这些概念，但它们更像评审辅助信息：人工告诉系统哪些文件应该在一起、哪些绝对不该在一起，然后我们拿这些标签辅助判断实验结果。读完这组材料之后，我的看法变得更强硬了：这些 pairwise constraints 不能继续只是注释或人工眼测提示，它们应该成为 V2 里正式的“契约语言”。为什么这么说？因为 constrained clustering 这整条研究线的共同前提就是：相比直接定义全局簇结构，给出“这两个东西必须在一起 / 绝不能在一起”通常更容易、更稳定、更接近真实用户知识。对 DITE 而言，这尤其成立。普通用户很难给出一整套完美簇划分，但很容易指出“这两个文件明显是同一份资料的不同格式”“这篇课程笔记绝不该和财务说明聚一起”。

S3C2 那篇文章给我的直接启发，是它把问题拆成两个更容易的分类子问题：先判断 pairwise relation，再用这些关系去支持后续聚类。虽然 DITE 未必会照搬它的神经网络结构，但这个思路非常值得学。当前我们经常试图让一个单一聚类器同时解决全部问题：找簇、分边界、处理冲突、解释错误。约束聚类路线提醒我，其实可以把一部分最困难的“全局结构判断”降解成更局部、更可解释的二元关系判断。翻译到 V2，就是：系统应该正式支持“候选文件对/候选簇对”的关系判定层。这个层既可以由规则完成，也可以由 cross-encoder、LLM，甚至未来的轻量分类器来完成。它的产出不一定直接改写全局簇标签，但它至少可以作为小簇合并、边界文件归属和实验评估的高优先级证据。换句话说，constraints 不只是评估标签，它们也可以成为推理中间层的语言。

而那篇 2023 年的 overview 则进一步扩大了我的视角：它说明 constrained clustering 不是单一算法，而是一整类“如何利用专家知识”的设计空间。对 DITE 来说，这个提醒很关键，因为我们很容易把 `must_link / must_not_link` 想成“以后也许可以加一点点弱监督”。但从这篇综述的角度看，更准确的说法应该是：DITE 已经拥有了进入 constrained clustering 语言体系的入口，只是还没认真使用它。V2 最现实的做法，未必是立刻训练一个半监督聚类器，而是把 constraints 向前推进两步。第一步，让它们成为正式评估指标，而不是松散说明：每次实验都要报告 must-link recall、must-not-link violation、constraint-induced fragmentation。第二步，让它们进入系统裁决逻辑：当某个候选合并违背了高置信 cannot-link，系统应当明确阻断；当两个小簇之间存在多条 must-link 证据，系统应当上调它们进入二阶段裁决的优先级。这样做不会把 DITE 变成复杂的学术半监督平台，却能立刻提升可解释性和行为一致性。

所以，这组文献最终给我的最大启发是：V2 不应该把用户或人工知识只当作最后的验尸报告，而应当把它们视为系统的正式接口之一。约束不一定要一开始就驱动整个聚类，但必须在评估和边界判定里拥有真实权重。对一个本地文件聚类工具来说，这比盲目追求全自动更现实，也更符合用户心智。因为用户真正关心的，不是算法是否“纯无监督”，而是系统是否能稳定尊重那些显而易见、不容违背的关系。
